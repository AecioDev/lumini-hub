# CLAUDE.md

Este arquivo orienta o Claude Code (claude.ai/code) ao trabalhar com o código deste repositório.

## Visão geral do projeto

O Lumini Hub é um sistema ERP com backend em microsserviços Go (`Backend/`) e frontend em Vite + React + Ant Design (`Frontend/`). É um **sistema novo, feito do zero**, e não uma migração nem uma reescrita de um sistema existente. Está organizado em módulos de ERP (CRM, Estoque/Produtos, Compras, Vendas/Caixas, Financeiro, Fiscal, Contabilidade), acompanhados em `Documentos/Planejamento/`. O módulo de Integrações (`api.integrations`, hoje pausado) conecta o sistema a serviços externos, como a Loja Integrada. O acesso a qualquer banco legado de cliente é feito por uma aplicação separada, fora deste sistema.

## Comandos

### Backend (Go, a partir de `Backend/`)
```powershell
.\run_services.bat        # sobe api.gateway (4000), api.auth (4001), api.core (4002) em janelas separadas
go build ./...             # compila todos os módulos do workspace
go test ./...               # roda os testes; os que precisam de Postgres são ignorados se TEST_DATABASE_URL não estiver definida (ver "Schema do banco, seed e testes")
```
Exige um PostgreSQL local na porta 5432 e um `Backend/.env` (ver `Backend/.env.example`; ele também documenta `DB_AUTO_MIGRATE`, `BOOTSTRAP_ADMIN_*` e `TEST_DATABASE_URL`).

Cada serviço é iniciado com `go run main.go` (é o que o `run_services.bat` faz), que compila **apenas o `main.go`**: tudo o que o `main.go` usa precisa estar nele ou em um pacote importado, nunca em outro arquivo do `package main` (passa em `go build .`, mas quebra o `go run main.go` com `undefined`). O `api.auth` tem um teste (`TestMainCompilaSozinho`) que protege isso.

Regerar o Swagger depois de adicionar ou alterar handlers (rodar a partir de `Backend/microservices/api.gateway/`):
```powershell
swag init -g main.go -d ./,../../common,../api.auth,../api.core --parseDependency
```

### Frontend (Vite + React, a partir de `Frontend/`)
```powershell
pnpm install
pnpm dev      # servidor Vite em http://localhost:3000 (porta fixada no vite.config.ts para bater com o CORS do gateway)
pnpm build    # tsc -b && vite build
pnpm lint     # eslint .
```
Não há executor de testes configurado no frontend. Exige um `Frontend/.env.local` com `VITE_API_URL` (padrão `http://localhost:4000/api`, ou seja, o gateway).

Login local: o usuário é `admin` e a senha é a que estava em `BOOTSTRAP_ADMIN_PASSWORD` no primeiro boot do banco (8 a 72 caracteres; remova a variável do `.env` depois). Um banco novo e vazio não tem usuários até que `BOOTSTRAP_ADMIN_*` seja definido (ver "Schema do banco, seed e testes"). Depois de entrar, a senha pode ser trocada pela tela de Usuários (a API aceita a partir de 6 caracteres).

## Arquitetura do backend

Go Workspace (`Backend/go.work`) com cinco módulos:
- **`common/`**: pacote compartilhado: `config` (leitura do ambiente), `database` (pool GORM/Postgres), `middlewares` (`AuthMiddleware` com JWT no cookie, `RequirePermission` para RBAC), `utils` (JWT, bcrypt, `response.go`, paginação), `repository` (`Repository[T]` / `GormRepository[T]` genéricos).
- **`microservices/api.gateway`** (porta 4000): única porta de entrada. Faz proxy reverso por prefixo de caminho para os outros serviços e é o **único** lugar onde o CORS é configurado.
- **`microservices/api.auth`** (porta 4001): usuários, perfis, permissões, itens de menu (árvore dinâmica da barra lateral), login/refresh (cookies HTTP-only).
- **`microservices/api.core`** (porta 4002): clientes, fornecedores, endereços, contatos, documentos, empresas (multiempresa, ver `Company` abaixo).
- **`microservices/api.integrations`** (porta 4007): integrações do sistema com serviços externos (hoje, a Loja Integrada), ver a [seção dedicada](#integrações-apiintegrations-porta-4007) abaixo.

```mermaid
graph TD
    Client[Frontend - Vite/React/antd<br>Porta 3000] -->|HTTP/API| Gateway[api.gateway<br>Porta 4000]
    Gateway -->|/api/auth, /api/users, /api/roles, /api/permissions, /api/menu-items| Auth[api.auth<br>Porta 4001]
    Gateway -->|/api/customers, /api/suppliers, /api/companies| Core[api.core<br>Porta 4002]
    Gateway -->|/api/integrations| Integrations[api.integrations<br>Porta 4007]
    Auth -.->|imports| Common[common]
    Core -.->|imports| Common
    Integrations -.->|imports| Common
    Auth --> PG[(PostgreSQL<br>Porta 5432)]
    Core --> PG
    Integrations --> PG
    Integrations <-->|webhook + REST| LI[Loja Integrada]
```

`api.auth`, `api.core` e `api.integrations` dividem, por enquanto, um único banco Postgres físico, mas nunca fazem join entre as tabelas uns dos outros. Dados entre serviços (por exemplo, o `User` dentro de um DTO de Customer) trafegam como IDs simples e são reidratados numa struct local simplificada (por exemplo, `ApiUser`), nunca como uma relação GORM.

### Padrões obrigatórios do backend
- **Respostas**: todo handler responde por `utils.SuccessResponse` / `utils.ErrorResponse` / `utils.ValidationErrorResponse` ([response.go](Backend/common/utils/response.go)). Nunca monte payloads `gin.H` à mão. O `utils.ErrorResponse` nunca envia ao cliente o texto de erro de um 500 (ele grava o erro no log do servidor, com método e caminho, e a resposta leva só a `message`): num 500 pode passar o `err.Error()` cru, mas nunca ponha erro bruto do banco num 4xx, onde o texto é mostrado ao usuário.
- **Repository**: os repositórios de cada microsserviço estendem o genérico `commonrepo.Repository[T]` e sobrescrevem métodos como `FindByID` quando é preciso `Preload` do GORM.
- **Unit of Work**: os services nunca tocam em um repository nem em um `*gorm.DB` diretamente: chamam `s.uow.Execute(func(uow repository.UnitOfWork) error { ... })` para que as escritas sejam atômicas. Cada microsserviço define a sua interface `UnitOfWork` (ver `api.core/internal/repository/repository.go`), com um método por agregado (`Customers()`, `Suppliers()`, ...). Exceções pontuais e documentadas são aceitáveis (por exemplo, `CompanyService.GetCompanies` entrega o `GetDB()` ao `utils.ResolveVisibleCompanyIDs`, compartilhado e só de leitura), mas apenas para leitura e com um comentário dizendo o motivo; nunca podem virar regra, e toda escrita passa sempre por `s.uow.Execute(...)`.
- **Busca**: consultas complexas ou paginadas são endpoints POST terminados em `/filter` (um DTO `<Entity>FilterRequest` com `page_no`, `page_size`, `order_by_column`, `is_asc`), e não GETs com query string. Os resultados passam por `utils.Paginate`.
- **Defesa contra SQL Injection**: todo valor que entra numa consulta vai como parâmetro (`?`), e o texto do SQL fica fixo: `query.Where("first_name ILIKE ?", "%"+filter.FirstName+"%")` (o `+` aqui junta o `%` ao *valor*, não ao SQL). Nunca concatene nem use `fmt.Sprintf` para pôr dado vindo do usuário dentro do texto de um `Where`/`Raw`/`Exec`/`Order`/`Joins`. Nome de coluna ou de ordenação que venha da requisição (`order_by_column`) só pode ser usado depois de conferido contra uma lista fixa de colunas permitidas. Isso vale também para o log: com `?` o valor não aparece no SQL.
- **CORS**: configurado somente em `api.gateway/main.go`. Colocá-lo no `api.auth` ou no `api.core` causa cabeçalho duplicado e `AxiosError: Network Error` no navegador.
- **RBAC (híbrido)**: um `Role` é só um modelo/padrão: ao criar ou editar um usuário escolhe-se um Role, que pré-preenche um conjunto padrão de permissões, mas o que o middleware `RequirePermission` de fato confere é a lista de permissões do vínculo direto `user_permissions` do próprio usuário (`api.auth/internal/domain/user.go`), e não a do Role. Os operadores podem adicionar ou revogar permissões individuais de um usuário além do padrão do Role (`PUT /users/:id/permissions`). O catálogo de Permissões (`/settings/permissions`) é uma tela só de desenvolvedor (`permissions.*` + `admin.create_permissions`): criar uma permissão ali não tem efeito se já não existir no código um `RequirePermission("...")` correspondente. O catálogo de Perfis (`/settings/roles`, mostrado como "Perfis e Permissões" na barra lateral, protegido por `roles.view`) pertence ao ADMIN.
- **O bypass de RBAC tem dois níveis** (`common/utils/rbac.go`, 2026-07-19): o `DEVELOP` passa por todas as checagens de `RequirePermission` e vê o menu inteiro, sem exceção. O `ADMIN` passa por tudo **exceto** a *escrita* no próprio catálogo de Perfis/Permissões (`utils.IsDeveloperOnlyPermission`: `admin.create_permissions` + qualquer código `permissions.*` **exceto** `permissions.view`, que continua aberto ao ADMIN porque as telas de criar/editar Usuário precisam dele para montar o seletor de permissões): criar/editar/excluir **Permissões** (`/settings/permissions`) é só do DEVELOP. O catálogo de **Perfis** (`roles.*`) pertence ao ADMIN: ele *não* é só de desenvolvedor no `rbac.go`, e a sua entrada na barra lateral ("Perfis e Permissões", `/settings/roles`) nasce no seed com `roles.view` (corrigido em 2026-10-01: este texto listava `roles.*` como só do DEVELOP, o que deixou de ser verdade em 2026-07-21, e o seeder ainda ligava essa entrada a `admin.create_permissions`, então um banco semeado do zero a escondia do ADMIN). Motivo: criar uma permissão sem um `RequirePermission("...")` correspondente no código não faz nada, então isso é uma ferramenta de desenvolvedor, não de administrador do negócio. O backend (`middlewares.RequirePermission`, `domain.FilterMenuTreeForUser`) e o frontend (`hasPermission` do `AuthContext.tsx`) implementam essa mesma divisão em níveis: mantenha os dois em sincronia se ela mudar. O seed (ver "Schema do banco, seed e testes") cria apenas o Role `ADMIN` e nunca o Role `DEVELOP` nem as permissões dele: o `DEVELOP` é criado e preenchido à mão no banco (`user_permissions`), em cada ambiente, pela equipe de desenvolvimento, e não por código. O seed também não vincula ao `ADMIN` as 9 permissões do módulo `Develop` (ele não precisa: o ADMIN passa pelo bypass).
- **O Role `DEVELOP` e os seus usuários são invisíveis para todos, exceto para o próprio DEVELOP** (`user_service.go`/`role_service.go`, 2026-07-20): `GET /users`/`GET /users/:id` nunca devolvem um usuário cujo Role seja `DEVELOP`, a menos que o Role do solicitante seja `DEVELOP` (filtrado no nível do SQL na listagem, com uma subconsulta `role_id NOT IN (SELECT id FROM roles WHERE name = 'DEVELOP')`, para que os totais da paginação continuem corretos; um `GET /users/:id` direto num usuário oculto devolve 404, não 403: a existência não é revelada). O mesmo tratamento vale para `GET /roles`/`GET /roles/:id` e para o CRUD do próprio Role (`UpdateRole`/`DeleteRole`/`UpdateRolePermissions` devolvem 404 para o Role DEVELOP quando o chamador não é DEVELOP). `CreateUser`/`UpdateUser` também recusam atribuir o ID do Role DEVELOP a um usuário, a menos que quem age seja DEVELOP (erro genérico "perfil inválido", que não revela o nome do Role). O Role do solicitante vem de `utils.RoleFromGinContext(c)` e é repassado pela camada de service como um parâmetro string simples: nenhum método de repository/service daqui recebe mais `isAdmin bool`, todos recebem `requesterRole string`.
- **Rotas**: prefixos de rota novos precisam ser registrados no arquivo de rotas do próprio microsserviço **e** repassados pelo `api.gateway/main.go` (via `router.NoRoute`, com cuidado para não colidir com `/swagger/*any`).

### Adicionar uma entidade nova (microsserviço Core ou Auth)
Siga esta ordem (ver `.claude/skills/lumini_hub_entity_creation/SKILL.md` para o detalhe completo):
1. `internal/models` (ou `domain`): struct GORM + `Create<Entity>Request`/`Update<Entity>Request` com tags de validação `binding`.
2. `internal/models/<entity>_dto.go`: DTOs + mapeadores `ToDTO()`/`ToDetailDTO()`.
3. `internal/repository/<entity>_repository.go`: interface que estende `commonrepo.Repository[domain.<Entity>]` + implementação GORM, com sobrescritas de `Preload` quando necessário.
4. `internal/validator/<entity>_validator.go`: validação de regras de negócio (unicidade, itens aninhados).
5. `internal/service/<entity>_service.go`: lógica de negócio, com todas as escritas dentro de `s.uow.Execute(...)`.
6. `internal/handlers/<entity>.go`: CRUD + busca `/filter`, anotações Swagger, helpers de resposta padrão.
7. `internal/routes/<entity>_routes.go`: registro no grupo do roteador Gin, com os middlewares de autenticação/perfil.
8. Ligue repository → validator → service → handler → rotas em `internal/server/server.go` (ou equivalente de inicialização).
9. Adicione a nova struct à cadeia de `AutoMigrate` do serviço (`prepareDatabase` no `api.auth/main.go`, ou `api.core/main.go`), na ordem de dependência das chaves estrangeiras. Isso só roda quando `DB_AUTO_MIGRATE` está ligada.
10. Semeie dados padrão, se for o caso: de forma idempotente e sob a mesma flag `DB_AUTO_MIGRATE` (os seeds do auth ficam em `api.auth/seed`).
11. Registre as permissões da entidade (`<entity>.view/create/edit/delete`) no `PermissionCatalog` (`api.auth/seed/permission_catalog.go`). O próximo boot as cria e as vincula ao `ADMIN` automaticamente (tudo que estiver fora do módulo `Develop`); vínculos que já existem nunca são tocados. Toda permissão que uma rota exige com `RequirePermission("...")` precisa estar no catálogo; do contrário só o ADMIN/DEVELOP poderá usar a rota (desde 2026-10-20, CFG-10.1, o catálogo cobre todo `RequirePermission` do código: mantenha assim ao adicionar rotas).
12. Regere o Swagger (comando acima).

Os nomes de arquivo são em snake_case (`customer_supplier_repository.go`), e os controllers nunca devem ligar diretamente nos repositories: sempre Service → UoW.

### Schema do banco, seed e testes (desde 2026-10-01)

Um Postgres novo e vazio sobe sozinho: os serviços criam as suas tabelas e o `api.auth` semeia os dados base. Planejado em `Documentos/Planejamento/Modulo_0_Configuracao/plano_schema_seed.md` (EPIC CFG-9).

- **`DB_AUTO_MIGRATE`** (`common/config`, padrão **true**; um valor inválido faz o `config.Load()` falhar, em vez de cair em silêncio no padrão). `true`: cada serviço roda o `AutoMigrate` das próprias tabelas (`api.auth`: Permission, Role, User, MenuItem; `api.core`: Company, CompanyFiscalConfig, Country, State, City, Customer, Supplier, Address, Document, Contact; `api.integrations`: as suas 4 tabelas do Postgres). `false` (produção com dados reais): nenhum serviço roda o `AutoMigrate`, e o `api.auth` também pula todo o seed (o `prepareDatabase` retorna de imediato), de modo que o operador assume o schema e os dados. Nesse caso o catálogo de permissões e o menu **não** são aplicados sozinhos: aplique-os por outro meio (por exemplo, rodar uma vez com a flag ligada, ou o futuro comando do binário do `api.auth`). Fora do alcance da flag: o `api.integrations` ainda roda o `ConfigService.SeedDefaults()` (chaves padrão em `integration_configs`), que precisa que essa tabela exista.
- **Boot do `api.auth`** (`prepareDatabase`, `api.auth/main.go`), tudo sob essa flag e nesta ordem: `AutoMigrate` → `seed.SyncCatalog` → `seed.BootstrapAdmin` → `seeder.SeedMenuItems` (o menu referencia permissões pelo código, por isso o catálogo vem primeiro) → `dbversion.Record` (ver abaixo). Com a flag desligada, o `prepareDatabase` só roda o `dbversion.Check`.
- **Versão do banco** (`common/dbversion`, tabela `schema_versions`, CFG-020): o banco registra em que versão está. `dbversion.Required` (a versão do banco que este código exige, o 2º número da versão do sistema) e `dbversion.AppVersion` (a versão completa do sistema) são duas constantes editadas **à mão a cada release**: `AppVersion` sempre, `Required` só quando o release traz mudanças de banco (+1; patches e releases sem mudança de banco mantêm o número). O `api.auth` chama `dbversion.Record` no fim de um boot bem-sucedido com `DB_AUTO_MIGRATE=true` (uma linha por release; reiniciar nunca duplica). Com `DB_AUTO_MIGRATE=false`, todo serviço (`api.auth`, `api.core`, `api.integrations`) chama `dbversion.Check` e **se recusa a subir** se o banco estiver atrás de `Required` ou sem versão registrada; um banco à frente do código não é erro. O operador atualiza o banco rodando o `api.auth` uma vez com a flag ligada (ou aplicando a atualização por outro meio). O `AutoMigrate` só adiciona, então mudanças que reescrevem dados existentes precisam de um script próprio.
- **`seed.SyncCatalog`** (pacote público `api.auth/seed`, importável como `lumini-hub/api.auth/seed`): o `PermissionCatalog` é a fonte única, em código, das permissões (transcrito do banco de desenvolvimento em 2026-10-01, mais as 8 permissões que o código exigia e o dev nunca teve, acrescentadas em 2026-10-20; a limpeza dos nomes das entradas herdadas é o EPIC CFG-10, CFG-10.2). Idempotente. Primeiro boot (nenhum role existente): cria o role `ADMIN` (o único role que o seed cria) e o vincula a toda permissão cujo `Module != "Develop"` (58 de 67). Boots seguintes: cria apenas as permissões *novas* do catálogo e vincula as novas que não são do Develop ao ADMIN; nunca refaz um vínculo que o operador removeu, nunca toca nem apaga permissões existentes (inclusive as criadas à mão e as apagadas com soft delete) e nunca cria outro role.
- **`seed.BootstrapAdmin`** (transitório: na fase multi-tenant um aplicativo comercial de provisionamento criará o primeiro admin): a partir de `BOOTSTRAP_ADMIN_USERNAME` (padrão `admin`), `BOOTSTRAP_ADMIN_PASSWORD` (**sem padrão**) e `BOOTSTRAP_ADMIN_EMAIL` (vazio vira `<username>@lumini.local`, porque `users.email` é único). Só roda se a tabela `users` estiver vazia (linhas com soft delete contam), então reiniciar nunca duplica o usuário nem muda a senha. Sem senha, não cria nada e só avisa. Senha: no mínimo 8 caracteres e no máximo 72 bytes (limite do bcrypt); qualquer outra coisa é erro de configuração e interrompe o boot. O usuário é `ADMIN`, ativo, sem `company_id` (master: vê todas as empresas, e por isso um banco sem empresa cai na etapa de cadastro de empresa do frontend). A senha nunca chega a logs nem a mensagens de erro, e `config.Config`/`AdminBootstrap` a imprimem como `<omitida>`. Remova a variável do ambiente depois do primeiro boot.
- **Sem seed de geografia**: países, estados e cidades devem ser criados sob demanda quando um CEP for consultado nas telas de Cliente/Fornecedor (funcionalidade futura). Observe que `Document.StateID` é um `uint` simples com FK para `state` (o valor zero viola a constraint, e a tabela `state` começa vazia; planejado: torná-lo um `*uint` opcional quando esse módulo for construído), e que `person_type` (hoje `text`, sem validação) deve virar um `F`/`J` validado.
- **Testes que precisam de Postgres** usam `testutil.OpenTestDB` (`common/testutil`): defina `TEST_DATABASE_URL=postgres://user:pass@host:5432/lumini_test?sslmode=disable` (ver `Backend/.env.example`). Sem ela, eles são **ignorados**. O helper recusa qualquer banco cujo nome real (`current_database()`) não termine em `_test`, exige o formato de URL e dá a cada teste um schema descartável (`t_<hex>`), de modo que os pacotes rodam em paralelo sem colidir e nada mais no banco é tocado. Nunca aponte para o banco de desenvolvimento. O `PermissionCatalog` é uma variável global, então os testes de `api.auth/seed` não podem usar `t.Parallel`.

## Arquitetura do frontend

Vite + React 18 + TypeScript + React Router v6 + Ant Design v5 (`antd`). O frontend foi reconstruído do zero em 2026-07-19: a pilha anterior (Next.js App Router + Tailwind + `rizzui`/Radix) foi inteiramente apagada e substituída, não estendida. Alias de caminho `@/*` → `Frontend/src/*`. O servidor de desenvolvimento é fixado na porta 3000 no `vite.config.ts`, necessário porque o CORS do gateway só permite `http://localhost:3000`/`:3001`.

Não existe mais a divisão de "UI híbrida" para o módulo de CRM: o `antd` é a única biblioteca de UI de todo o app agora (sem Tailwind, sem rizzui/Radix).

- **`src/types/`**: um arquivo por entidade, com interfaces TS espelhando os DTOs Go do backend (`auth.ts`, `user.ts`, `role.ts`, `permission.ts`, `menu.ts`, `customer.ts`, `supplier.ts`), mais o `common.ts` com o envelope compartilhado `ApiResponse<T>`/`ApiPagination`. O `crm.ts` é explicitamente só de mock (ver abaixo).
- **`src/services/`**: um arquivo por entidade (`auth/auth-service.ts`, `users/user-service.ts`, `roles/role-service.ts`, `permissions/permission-service.ts`, `customers/customer-service.ts`, `suppliers/supplier-service.ts`), cada um envolvendo a instância compartilhada do axios. Nenhuma página/componente chama o axios diretamente.
- **`src/services/common/api.ts`**: o único cliente axios (`withCredentials: true`, URL base vinda de `VITE_API_URL`). O interceptor de resposta tenta de novo uma vez, via `/auth/refresh-token`, num 401 (pulando as próprias chamadas de login/refresh); se o refresh falhar, redireciona à força para `/login`, **exceto** na chamada inicial de `/auth/me` (que inicia a sessão), que é deixada falhar com elegância pelo `AuthContext` + o redirecionamento SPA do `ProtectedRoute`, em vez de forçar um recarregamento completo da página.
- **`src/schemas/`**: um schema Zod por formulário (`login-schema.ts`, `forgot-password-schema.ts`, `create-user-schema.ts`, `update-user-schema.ts`), com validação alinhada às tags `binding` do backend.
- **`src/contexts/`**: `AuthContext.tsx` (inicia a sessão via `GET /auth/me` no carregamento e expõe `user`, `menuItems`, `login()`, `logout()`, `hasPermission()`) e `ThemeContext.tsx` (escuro/claro, guardado no `localStorage`, alimenta o `theme.darkAlgorithm`/`defaultAlgorithm` do `ConfigProvider` por meio de `src/theme/antd-theme.ts`).
- **`src/routes/`**: `router.tsx` (árvore de rotas), `ProtectedRoute.tsx` (porta de entrada da sessão), `RequirePermission.tsx` (porta de permissão por rota: só conveniência de UI, a verdadeira checagem é o middleware `RequirePermission` do backend), `AuthLayout.tsx` (casca com cartão centralizado para Login/Recuperar senha), `AppLayout.tsx` (`Layout.Sider` recolhível de 240/76px + `Layout.Header` + `Layout.Content`).
- **`src/pages/`** / **`src/components/`**: organizados por domínio (`pages/auth/`, `pages/dashboard/`, `pages/users/`; `components/layout/`, `components/dashboard/`, `components/users/forms/`, `components/common/`). O `pages/PlaceholderPage.tsx` é a tela padrão para qualquer `href` de menu vindo do banco que ainda não tenha uma tela de verdade.
- Todas as chamadas de API passam pelo gateway (`http://localhost:4000/api/...`), nunca direto para as portas do `api.auth`/`api.core`.

### O menu lateral vem dos dados, não é fixo no código

A barra lateral (`src/components/layout/SidebarMenu.tsx`, `Menu` do antd recursivo, de profundidade arbitrária) é montada a partir de `user.menuItems`, que vem no corpo da resposta de login/refresh/me, **não** de um arquivo de configuração estático. A fonte da verdade é a tabela `menu_items` do `api.auth` (domínio `MenuItem` autorreferenciado, `internal/domain/menu_item.go`), gerenciada por `/menu-items` (só de desenvolvedor, protegido por `admin.create_permissions`, ainda sem tela de administração: apenas CRUD). O `AuthService.GetMenuItemsForUser` monta a árvore e a filtra por usuário (o ADMIN vê tudo; um nó com `href` precisa da sua própria permissão vinculada ou do bypass do ADMIN; um nó de grupo puro, sem `href`, só fica visível se tiver algum descendente visível: nunca conceda acesso a ele por conta própria, já que não tem permissão própria para checar). Os ícones são strings do Iconify (prefixo `ph:` = Phosphor), resolvidas pelo componente `<Icon>` do `@iconify/react`, e não por JSX. **As `key`s dos itens do `Menu` do antd devem ser montadas a partir do `id` do item, não do seu `href`**: a árvore semeada de verdade tem hrefs duplicados em posições diferentes (por exemplo, "Clientes" aparece em Vendas > Cadastros e em Financeiro > Contas a Receber, ambos apontando para `/customers`), o que colide se o `href` for usado como chave. Os hrefs semeados são caminhos aninhados como `/settings/users`, não planos: confira sempre os `menu_items` da resposta real de login antes de ligar uma rota nova no frontend, não presuma o caminho. Para mudar a árvore do menu, edite as linhas de `menu_items` (ou, para os padrões do seed, `internal/seeder/menu_item_seeder.go`).

### Padrão obrigatório de CRUD no frontend

O Cadastro (criação) e a Edição de uma entidade são **páginas inteiras**, não modais: por exemplo `src/pages/users/CreateUserPage.tsx` / `EditUserPage.tsx`, registradas em `src/routes/router.tsx`, cada uma renderizando um componente de formulário de `src/components/<domain>/forms/` (por exemplo `CreateUserForm.tsx`/`EditUserForm.tsx`). A validação é `react-hook-form` + `zodResolver` com um schema em `src/schemas/`, reaproveitando o wrapper compartilhado `FormField` (`src/components/common/FormField.tsx`, camada fina sobre o `Form.Item` do antd) para o rótulo e a exibição do erro. Formulários complexos são divididos em `antd Tabs` (por exemplo "Dados do Usuário" e "Permissões"), em vez de uma rolagem longa. No envio, `navigate()` de volta à rota da lista; o `message`/`notification` de `App.useApp()` dá o retorno ao usuário.

Os modais são reservados para **confirmar ações destrutivas ou do usuário**: nunca para formulários de entrada de dados.

As subseções que não são gerenciadas pelo Zod (por exemplo, o seletor de Perfil/permissões ligado a um usuário mas que não é um campo do formulário) ficam como `useState` irmão no componente do formulário, e não dentro do schema do RHF: ver `CreateUserForm.tsx`/`EditUserForm.tsx`: os botões de pré-seleção de Perfil (`RolePresetPicker.tsx`, perfis buscados ao vivo em `GET /roles`) controlam o `ModulePermissionsPanel.tsx`, que mostra só as permissões do módulo cujo nome bate com o Perfil selecionado, voltando ao primeiro módulo com alguma permissão marcada quando os nomes não batem (a nomenclatura de Role/módulo no catálogo semeado ainda não é totalmente consistente: por exemplo, os roles "Gerente"/"ADMIN" não têm módulo de mesmo nome).

Este padrão está totalmente implementado para **Usuários** (`/settings/users`) e **Empresas** (`/settings/companies`, acrescentado em 2026-07-27 como parte da base multiempresa: `src/pages/settings/companies/`, `company-service.ts`, `company-schema.ts`). O frontend foi reconstruído do zero em 2026-07-19; Login, Recuperar senha (só UI, ainda sem endpoint no backend), Dashboard de CRM (com dados simulados, ainda sem backend `api.crm`) e Configurações → Integrações (real, ver `api.integrations` acima) completam o que é real hoje: todo outro destino da barra lateral cai no `PlaceholderPage`. Aplique este padrão ao construir cada um deles.

### Campos com máscara (CPF/CNPJ/telefone/CEP): máscara na tela, só dígitos no banco

Decidido em 2026-09-05, vale para todo campo desse tipo, passado e futuro (`Company.cnpj`, qualquer campo futuro de telefone/CEP etc.): o frontend mostra e recebe a digitação com a máscara (melhor UX, e o próprio formato da máscara já é uma validação de formato gratuita no cliente: por exemplo, recusar um CNPJ com a quantidade errada de dígitos enquanto se digita), mas **somente os dígitos puros são enviados ao backend e gravados no banco**: nunca persista a pontuação. Ainda não há biblioteca de máscara instalada (conferido em 2026-09-05); ao construir ou mexer num campo assim, adicione uma (ou um pequeno helper local de máscara), em vez de gravar a string mascarada como está. Isso diz respeito só ao frontend: os campos de request/DTO do backend para esses valores são sempre strings de dígitos simples, sem validação de formato no backend além de tamanho/dígito verificador, se for o caso.

### Campos brasileiros de documento/endereço mantêm o nome brasileiro, não uma tradução literal para o inglês

Decidido em 2026-09-05: a convenção de nomes do projeto é identificadores em inglês, mas alguns tipos de documento legal/postal brasileiros são tão específicos e universalmente chamados pela sua sigla em português (na conversa, na UI, na cabeça de todo desenvolvedor brasileiro) que traduzi-los literalmente atrapalha a clareza em vez de ajudar: `CNPJ`/`CPF`/`CEP`/`RG` não são "TaxID"/"PersonalID"/"PostalCode"/qualquer outra coisa, são vocabulário de domínio. Exemplo: `Company.TaxID` foi renomeado para `Company.CNPJ` (campo Go, chave JSON `cnpj`, coluna do banco `cnpj`, campo TS, chave do schema Zod); a mesma regra vale para CPF/CEP/RG onde aparecerem a seguir (por exemplo, o campo CEP de uma futura entidade Address). Mantenha a própria sigla em português/maiúscula como identificador em todas as camadas (campo de struct Go, tag JSON, coluna do banco, tipo TS): não invente uma tradução em inglês. Isso **não** se estende a substantivos comuns de negócio que apenas são ditos em português na conversa (`empresa` continua virando `Company`, `usuário` continua virando `User`): vale só para essas siglas fixas de documentos legais/postais.

### Toda lista/grid mostra o ID do registro

Decidido em 2026-09-05: toda tabela/grid que lista uma entidade salva (`CompaniesTable`, `UsersListPage` etc.) mostra o `id` do registro como coluna, a primeira, a menos que haja um bom motivo para não (o ID não existe como conceito estável naquela visão, ou o usuário pede expressamente para deixá-lo de fora numa tela específica). Custa pouco e é a forma mais rápida de cruzar uma linha com logs, o banco ou uma conversa de suporte.

## Fluxo de trabalho / Planejamento

Quem conduz o trabalho é o usuário: toda tarefa começa numa conversa com ele, e nada roda sozinho. Não há subagentes, quadro Kanban nem acompanhamento automático de tarefas neste projeto (removidos em 2026-10-20). Não crie agentes a menos que o usuário peça.

- `Documentos/Planejamento/` guarda o escopo e o histórico de cada módulo (`Modulo_0_Configuracao` ... `Modulo_9_Integracoes`): `plano_*.md` (escopo, banco, regras de negócio, arquivos afetados). Os `tasks_*.md` de trabalhos fechados estão em `Documentos/Planejamento/Arquivo/` (só consulta); o único que continua na pasta do módulo é o `tasks_integrations.md` (Módulo 9, pausado). O `Documentos/Planejamento/README.md` explica a organização.
- Leia esses arquivos só quando o usuário apontar um módulo/funcionalidade, ou quando precisar das regras de negócio da tarefa em mãos. Os arquivos de `Arquivo/` são muito grandes (o `tasks_empresa.md` tem cerca de 330 KB): busque o trecho relevante, nunca leia o arquivo inteiro.
- **O controle do trabalho fica em dois arquivos pequenos em `Documentos/Planejamento/`**: `BACKLOG.md` (o que foi feito e o que falta, `[ ]`/`[x]`; todo item tem um ID `PREFIXO-NNN`, como `CFG-014`, sendo o prefixo o módulo da tabela no topo desse arquivo e o número sequencial por prefixo e nunca reaproveitado; dê a todo item novo o próximo ID livre e cite-o no `PROXIMA_VERSAO.md`; só o usuário marca `[x]`, depois de testar ele mesmo) e `PROXIMA_VERSAO.md` (mudanças feitas desde o último envio ao servidor). Quando terminar uma tarefa que o usuário pediu, acrescente uma linha ao `PROXIMA_VERSAO.md` e mostre-a; se a tarefa estiver no `BACKLOG.md`, mantenha-a `[ ]` com a nota `(implementado, aguardando teste)`. Quando o usuário pedir um release, leia o `PROXIMA_VERSAO.md`, atualize as constantes em `Backend/common/dbversion/dbversion.go` (`AppVersion` sempre, `Required` só se o release tiver mudanças de banco), escreva `releases/Release_<versão>.md` no formato de `releases/Release_2026.2.2.0.md` (um app de portal lê esses arquivos, então mantenha a estrutura exata: título `# Lumini Hub — Release <versão>`, um cabeçalho com versão do sistema, versão do banco e tema, a data de geração e a legenda ✅ testado · ⚠️ implementado, ainda não testado · ⏳ pendente, depois as seções 1 Banco de dados, 2 Novidades, 3 Correções, 4 Infraestrutura, 5 Configuração necessária no servidor, 6 Arquivos principais alterados / criados e 7 Pendências conhecidas em forma de tabela; tire as marcas ✅/⚠️ do que o usuário realmente testou, nunca presuma; o release vai para um portal, então nunca escreva nele IP, endereço ou nome de servidor, nomes de usuários e de dados de teste nem valores de senhas ou segredos: nomes de variáveis de ambiente podem aparecer, valores nunca) e então zere o `PROXIMA_VERSAO.md`. Formato da versão: `ano.versao_do_banco.sequencia_versao.sequencia_patch`: o 2º número é a versão do banco e sobe uma unidade por release publicado que contém mudanças de banco (não por mudança individual: dez colunas novas e uma tabela no mesmo release contam como uma só), e todo release deve listar o que mudou no banco. A versão atual nunca fica escrita nestas instruções: leia `AppVersion` e `Required` em `Backend/common/dbversion/dbversion.go` (a versão do código), o `PROXIMA_VERSAO.md` (o que está pendente para a próxima) e o último arquivo de `Documentos/Planejamento/releases/` (o que foi publicado por último).
- Não edite os `tasks_*.md` (os arquivados e o `tasks_integrations.md`) nem escreva `Historico/log_*.md` a menos que o usuário peça. Os status deles (`[EM-TESTE]`, `[ENTREGUE]`, ...) são históricos: trate-os como informação, não como um fluxo a continuar alimentando.
- **Automação de navegador (`agent-browser`, o navegador embutido, capturas de tela, teste exploratório) só quando o usuário pedir**, ou quando for claramente a única forma de responder à pergunta. Prefira ler código, logs e testes primeiro; é um custo grande de tokens.
